# Buzz Remote Agent Protocol (BRAP) v1

## Goal

Run a normal Buzz managed agent on another server without opening an inbound
port on that server and without sending an agent private key, provider secret,
or shell credential from the desktop to a third-party deployment provider.

The remote worker makes one outbound WebSocket connection to the normal Buzz
relay. The desktop already connects to that relay, so neither endpoint needs a
direct route to the other.

## Security properties

- Transport requires `wss://` outside loopback development.
- Relay authentication uses NIP-42.
- Every control message is a signed NIP-01 event.
- Every control payload is encrypted end to end with the audited NIP-44 v2
  implementation from `nostr-tools`.
- The outer event signature is verified before decryption.
- Enrollment credentials are random, one-time, narrowly scoped, expire in ten
  minutes by default, and are stored only as hashes.
- The remote worker generates and stores its Nostr private key locally. It
  never returns that key to the owner, desktop, relay, logs, status messages,
  snapshots, or provider APIs.
- Commands are bound to owner, worker, deployment, session, sequence, issued
  time, and expiry.
- Replayed, expired, reordered, cross-deployment, and cross-recipient messages
  fail closed.
- Revocation prevents new sessions and command processing. A local kill switch
  on the worker always wins over remote commands.
- Secrets are sent only as explicitly named secret references. Plaintext
  provider API keys are not valid deployment configuration.

## Trust model

The relay is trusted for availability, membership enforcement, and routing but
does not need plaintext access to remote control payloads. It can observe
sender/recipient public keys, event kinds, timestamps, sizes, and traffic
patterns.

The owner identity is authorized to define and control its agents. The remote
worker identity is authorized only for its assigned deployments and cannot
impersonate the owner. The agent identity is generated by the worker and is a
separate key from the worker control identity, limiting the blast radius of
either key.

NIP-44 does not provide forward secrecy or post-compromise security. BRAP
therefore uses short-lived control sessions, does not persist control events,
does not send raw long-lived secrets, and supports immediate worker and
deployment key revocation.

## Identities

- **Owner key**: existing Buzz user/owner Nostr key.
- **Worker control key**: generated on the remote host during enrollment and
  stored in its OS keyring or a mode-0600 encrypted state file.
- **Agent key**: generated per deployment on the remote host and used by the
  ACP harness as the normal Buzz agent identity.
- **Relay key**: existing relay signing/authentication identity.

## Event kinds

All BRAP events are ephemeral and must never be persisted or indexed.

| Kind | Name | Direction |
| ---: | --- | --- |
| 24210 | `REMOTE_AGENT_ENROLLMENT` | worker to owner |
| 24211 | `REMOTE_AGENT_COMMAND` | owner to worker |
| 24212 | `REMOTE_AGENT_STATUS` | worker to owner |
| 24213 | `REMOTE_AGENT_ACK` | either direction |

These values live next to the existing agent observer ephemeral range and must
be added to the central kind registry in every client.

## Envelope

The outer object is a normal signed Nostr event. Required tags:

```json
[
  ["p", "<recipient-pubkey>"],
  ["worker", "<worker-pubkey>"],
  ["deployment", "<uuid>"],
  ["session", "<128-bit-random-hex>"],
  ["sequence", "<unsigned-decimal>"],
  ["message", "<uuid>"],
  ["expires", "<unix-seconds>"],
  ["protocol", "brap/1"]
]
```

`content` is a NIP-44 v2 ciphertext. Its plaintext is a strict JSON object:

```json
{
  "version": 1,
  "type": "command",
  "messageId": "a UUID",
  "deploymentId": "a UUID",
  "sessionId": "32 lowercase hex characters",
  "sequence": 4,
  "issuedAt": 1785250000,
  "expiresAt": 1785250030,
  "body": {}
}
```

The receiver validates, in this order:

1. encoded event and ciphertext byte limits;
2. NIP-01 event ID and signature;
3. expected event kind and sender;
4. exact recipient `p` tag;
5. exact protocol, worker, deployment, session, and sequence tags;
6. created-at and expiry windows;
7. message ID has not been seen;
8. sequence is the next accepted value for the session;
9. NIP-44 decryption;
10. strict payload schema and equality between signed tags and plaintext;
11. command-specific capability and lifecycle policy.

State is advanced only after all checks pass. Failed messages never consume a
sequence number.

## Enrollment

### Owner

1. Select **Add remote server**.
2. The relay creates 32 random bytes and returns a one-time token:
   `brap1_<enrollment-id>_<owner-pubkey>_<secret>`. The public owner key lets
   the worker encrypt its first enrollment event without a second setup API.
3. The relay stores only `SHA-256(secret)`, owner pubkey, community,
   capabilities, expiry, and an unused marker.
4. The UI displays one command. It never writes the token to normal logs.

### Remote server

```bash
buzz-remote-agent \
  --relay wss://buzz.example.com/ \
  --enrollment-token 'brap1_...'
```

1. The worker rejects non-`wss://` URLs unless the host is loopback and
   `--allow-insecure-localhost` is explicitly supplied.
2. It generates its worker key locally.
3. It connects outbound and completes NIP-42 authentication.
4. It redeems the token once and signs an enrollment proof bound to the relay
   challenge, owner, community, worker pubkey, and token ID.
5. The relay atomically marks the token used and publishes the encrypted
   enrollment request to the owner.
6. The owner approves the worker fingerprint in Buzz.
7. Both sides store the approved owner/worker binding.

Token redemption and approval are separate so possession of a leaked one-time
token cannot silently create an active worker.

## Session establishment

After enrollment or reconnect:

1. Worker sends `status:hello` with a new random session ID, sequence `0`,
   supported protocol versions, runtime capabilities, and a fresh nonce.
2. Owner replies `ack:hello`, encrypted to the worker, echoing the nonce and
   declaring the granted capabilities.
3. Worker accepts commands starting at sequence `1`.

Only one active session per worker/deployment is accepted. A newer approved
session invalidates the previous session. Reconnect uses exponential backoff
with jitter and a ceiling; it never creates concurrent command sockets.

## Commands

Initial v1 command allowlist:

- `deploy`: create an agent key locally and start its ACP harness.
- `start`: start an existing stopped deployment.
- `stop`: gracefully stop the harness, then force it after a bounded timeout.
- `restart`: stop and start with the current accepted configuration.
- `update`: apply a versioned non-secret configuration and restart if needed.
- `status`: return bounded health and version information.
- `logs`: return a bounded, redacted tail when the owner explicitly requests
  it and the worker grants the capability.
- `revoke`: stop the deployment, erase its control authorization, and optionally
  erase the local agent key after an explicit destructive confirmation value.

There is no generic shell command in BRAP. Agent tool execution continues
through ACP/MCP permission policy; remote management cannot be escalated into
an arbitrary host command channel.

## Deployment configuration

Allowed fields are schema validated and size limited:

- display name, system prompt, runtime ID, model, provider ID;
- ACP timing, parallelism, response policy, and public allowlist;
- channel/team/persona identifiers;
- MCP server descriptors from an explicit worker allowlist;
- secret references such as `env://ANTHROPIC_API_KEY`.

The worker resolves secret references from its own environment, keyring, or
configured secret manager. Unknown references fail deployment. Secret values
are excluded from acknowledgements, snapshots, process listings where
possible, logs, and error messages.

## Status and acknowledgements

Every accepted command produces an ACK with the same message ID:

- `accepted`: durable intent accepted;
- `completed`: requested transition completed;
- `rejected`: safe, user-facing reason and stable error code.

Long operations first ACK `accepted`, then emit status transitions. Status
payloads have strict size limits and redact configured secret values, Nostr
private keys, bearer tokens, and common provider-key formats.

## Revocation and deletion

**Revoke access** and **delete local definition** are separate operations.

1. Owner sends a signed, encrypted `revoke` command through the BRAP control
   operation while the worker is online.
2. Relay durably revokes the owner/worker binding immediately, then routes the
   encrypted erase instruction over the worker's existing socket.
3. Worker stops affected processes, persists its revoked state, optionally
   erases the local agent key, sends a final bounded acknowledgement, and
   closes its connection.
4. Desktop removes local control state only after observing revocation, or
   after the user explicitly chooses a forced local removal that warns the
   remote host may be orphaned.

If the worker is offline, the owner calls the NIP-98-authenticated relay
revocation endpoint. Relay-side revocation still prevents command routing on a
later authenticated socket. Local erasure on the offline server requires its
operator because the relay cannot deliver ciphertext to a disconnected host.

## Operational limits

- Maximum outer event: 256 KiB.
- Maximum decrypted control payload: 64 KiB.
- Default command lifetime: 30 seconds; maximum: 5 minutes.
- Clock skew tolerance: 60 seconds.
- ACK cache and message replay window: at least 15 minutes.
- Heartbeat: 20 seconds with randomized jitter; offline after three missed
  intervals.
- Log response: 48 KiB maximum and 2,000 lines maximum.
- One connection and one active session per worker.
- Per-worker and per-owner token-bucket rate limits.

## Protocol errors

Errors use stable codes and do not echo ciphertext, tokens, signatures, keys,
environment values, raw child-process stderr, or stack traces. Examples:

- `AUTH_REQUIRED`
- `ENROLLMENT_EXPIRED`
- `ENROLLMENT_USED`
- `OWNER_APPROVAL_REQUIRED`
- `SIGNATURE_INVALID`
- `RECIPIENT_MISMATCH`
- `MESSAGE_EXPIRED`
- `REPLAY_DETECTED`
- `SEQUENCE_INVALID`
- `CAPABILITY_DENIED`
- `DEPLOYMENT_NOT_FOUND`
- `CONFIG_INVALID`
- `SECRET_REFERENCE_MISSING`
- `PROTOCOL_VERSION_UNSUPPORTED`

## Compatibility

A remote agent publishes the same profile, presence, channel, message,
observer, and usage events as a local agent. Clients do not special-case its
chat behavior. Only managed lifecycle, log access, and host location differ.
